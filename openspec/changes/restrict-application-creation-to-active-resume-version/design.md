## Context

当前投递记录创建链路只校验了“归属关系”，没有校验 `resumeVersionId` 对应的简历版本是否处于激活状态。这样会导致未激活版本也能继续新增投递，和“激活版本代表当前用于外部投递的版本”这一业务含义不一致。

前端简历版本详情页目前也没有根据版本激活状态控制“新增投递记录”入口；岗位详情页发起投递时，则是直接进入投递创建页，当前链路里并没有把“激活版本约束”显式前置。为了避免只改一个入口而留下绕过点，本次需要同时覆盖版本详情入口、岗位关联入口和后端创建校验。

## Goals / Non-Goals

**Goals:**

- 只有激活的简历版本可以新增投递记录。
- 未激活版本仍可查看既有历史投递记录。
- 前端入口要显式收敛，不让用户从未激活版本详情页继续发起新增。
- 后端要阻止绕过前端的手工请求。

**Non-Goals:**

- 不禁止查看或回溯未激活版本已有的投递历史。
- 不重做“编辑已有投递记录”的权限体系。
- 不改变“同仓库仅一个版本激活”的现有规则。

## Decisions

### 1. 创建投递时必须校验简历版本激活状态

在 `resume_application` 创建流程中，先确认版本归属，再确认 `isActive`。如果版本未激活，直接拒绝创建，不写入新记录。

理由：后端是最终准入点，单靠前端隐藏按钮不能防止构造请求。

### 2. 简历版本详情页仅在激活版本展示新增入口

简历版本详情页继续展示历史投递列表，但只有激活版本才渲染“新增投递记录”按钮。

理由：这和业务语义最一致，也能减少用户误点。

### 3. 岗位详情到投递创建的链路也必须经过激活版本约束

岗位详情页进入投递创建页时，不能默认绕过版本状态校验。若当前创建页没有拿到可用的激活版本上下文，就必须阻止提交并引导用户先选激活版本。

理由：当前创建页同时承载“岗位带入”与“简历版本绑定”，如果不补这一层，岗位入口会变成新的绕过点。

### 4. 对外错误语义使用业务拒绝，不复用登录/认证错误

未激活版本不应返回 `40100` 这类认证错误；更合适的是业务拒绝语义，前端只显示明确的“简历版本未激活，不能新增投递记录”。

理由：这属于业务状态限制，不是登录态问题。

## Risks / Trade-offs

- [Risk] 岗位详情进入创建页时，当前代码没有现成的简历版本选择器。→ Mitigation: 任务中需要补齐一个明确的激活版本入口或提交前拦截。
- [Risk] 如果只隐藏按钮但不补后端校验，手工请求仍可绕过。→ Mitigation: 后端创建校验必须同时落地。
- [Risk] 如果把限制只加在版本详情页，岗位详情入口会成为漏洞。→ Mitigation: 两条入口都要覆盖。
